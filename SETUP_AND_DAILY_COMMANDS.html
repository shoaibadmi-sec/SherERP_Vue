Assumes Docker and PostgreSQL are already installed inside WSL2 Debian, and git init is already done in ~/projects/shererp. Stack is final — see SRS_AND_BUILD_GUIDE.md §1.3. Do not substitute anything.

01WSL2 daily commands

From Windows (PowerShell / Terminal)

wsl -l -v                      # list distros + state + WSL version
wsl -d Debian                  # open Debian shell
wsl --shutdown                 # hard restart ALL distros (fixes most weirdness)
wsl -t Debian                  # terminate just Debian
wsl --set-default Debian       # make Debian the default distro
wsl --status                   # WSL version + kernel
wsl --update                   # update the WSL kernel
Rule: code never lives under /mnt/c/ Keep the repo at ~/projects/shererp (the Linux filesystem). /mnt/c/ is roughly 10× slower for node_modules and file watching breaks. Edit from Windows via VS Code Remote — WSL, not by opening the \\wsl.localhost path in a Windows editor.

Inside Debian

pwd                            # where am I
cd ~/projects/shererp          # go to the project
ls -la                         # list including dotfiles
df -h .                        # disk space left
free -h                        # RAM in use (WSL VM)
htop                           # process viewer (sudo apt install htop)
explorer.exe .                 # open current folder in Windows Explorer
code .                         # open current folder in VS Code (WSL Remote)
hostname -I                    # WSL IP (for LAN access to the dev server)
sudo apt update && sudo apt upgrade -y

Ports and processes

ss -tulpn | grep LISTEN        # what is listening
ss -tulpn | grep 3000          # is the API port taken
lsof -i :3000                  # which process owns port 3000
kill -9 <PID>                  # kill it
pkill -f "nest start"          # kill a stuck Nest dev server
Memory limit (optional but recommended) On Windows create C:\Users\Shoaib\.wslconfig, then run wsl --shutdown: 
[wsl2]
memory=8GB
processors=4
swap=2GB

02zsh setup & project aliases

Everything below assumes zsh. Your config file is ~/.zshrc — not ~/.bashrc. This matters most for nvm, which will silently not exist in new shells if it is added to the wrong file.

echo $SHELL                    # should print /usr/bin/zsh or /bin/zsh
chsh -s $(which zsh)           # make zsh the login shell if it is not
nano ~/.zshrc                  # edit config
source ~/.zshrc                # reload config in the current shell
exec zsh                       # or replace the shell entirely

Add to the end of ~/.zshrc

# ---------- nvm (MUST be in .zshrc, not .bashrc) ----------
export NVM_DIR="$HOME/.nvm"
[ -s "$NVM_DIR/nvm.sh" ] && \. "$NVM_DIR/nvm.sh"
[ -s "$NVM_DIR/bash_completion" ] && \. "$NVM_DIR/bash_completion"

# ---------- pnpm ----------
export PNPM_HOME="$HOME/.local/share/pnpm"
case ":$PATH:" in
  *":$PNPM_HOME:"*) ;;
  *) export PATH="$PNPM_HOME:$PATH" ;;
esac

# ---------- SherERP shortcuts ----------
export SHER=~/projects/shererp
alias sher='cd $SHER'
alias pg-up='docker start sher-pg'
alias pg-down='docker stop sher-pg'
alias pg-log='docker logs -f --tail 50 sher-pg'
alias psql-dev='docker exec -it sher-pg psql -U postgres -d sher_dev'
alias psql-test='docker exec -it sher-pg psql -U postgres -d sher_test'
alias dev='cd $SHER && pnpm dev'
alias check='cd $SHER && pnpm lint && pnpm typecheck && pnpm test:boundaries && pnpm test'
alias gs='git status -sb'
alias gd='git diff'
alias gl='git log --oneline --graph --decorate -15'

03Docker + PostgreSQL — daily use

Docker and Postgres are already installed. This section is what you actually type each day.

Every morning

sudo service docker start      # Docker Engine does not autostart in WSL2
docker start sher-pg           # start the database container
docker ps                      # confirm it is Up
Make Docker start itself Add to ~/.zshrc so you never hit "Cannot connect to the Docker daemon": 
if ! service docker status > /dev/null 2>&1; then
  sudo service docker start > /dev/null 2>&1
fi
For passwordless start: sudo visudo → add shoaib ALL=(ALL) NOPASSWD: /usr/sbin/service docker *

Container commands

docker ps                      # running containers
docker ps -a                   # all containers, including stopped
docker start sher-pg
docker stop sher-pg
docker restart sher-pg
docker logs -f --tail 50 sher-pg
docker stats sher-pg           # live CPU/RAM
docker exec -it sher-pg bash   # shell inside the container

Two databases — this is deliberate

DatabaseUsed byWhy separate
sher_devManual testing in the UIHolds your hand-entered acceptance data
sher_testpnpm testTest runs truncate tables — sharing one wipes your data mid-acceptance
# confirm both exist
docker exec -it sher-pg psql -U postgres -c "\l"

# create sher_test if it is missing
docker exec -it sher-pg psql -U postgres -c "CREATE DATABASE sher_test;"

psql — the queries you will actually run

psql-dev                       # your alias

\l                             # list databases
\dt                            # list tables
\d products                    # describe a table
\x                             # toggle expanded row output — use for wide rows
\q                             # quit

SELECT count(*) FROM products;
SELECT * FROM stock_movement ORDER BY created_at DESC LIMIT 20;
SELECT account, SUM(debit_minor) - SUM(credit_minor) AS balance
  FROM journal_line GROUP BY account ORDER BY account;
The journal query above is your correctness check Every posted document must leave Σ debit = Σ credit. If that query's total across all accounts is not zero, something in the write path is wrong — stop and report before building the next slice.

Backup and reset while developing

# dump sher_dev before a risky migration
docker exec sher-pg pg_dump -U postgres sher_dev > ~/backups/sher_dev_$(date +%F_%H%M).sql

# restore
cat ~/backups/sher_dev_2026-08-16_0930.sql | docker exec -i sher-pg psql -U postgres -d sher_dev

# nuke and recreate dev data (early phases only)
docker exec -it sher-pg psql -U postgres -c "DROP DATABASE sher_dev;"
docker exec -it sher-pg psql -U postgres -c "CREATE DATABASE sher_dev;"
pnpm db:migrate

05Monorepo skeleton Phase 0.1

This is slice 0.1 in AI_CODING_INSTRUCTIONS.md. In practice you paste that task block to the coding agent — but you need to be able to recognise and verify what it produces. Target layout:

shererp/ ├── package.json root scripts + devDependencies ├── pnpm-workspace.yaml workspace globs ├── tsconfig.base.json shared TS config ├── eslint.config.js ├── .nvmrc 20 ├── .gitignore ├── .github/workflows/ci.yml lint → typecheck → boundaries → test ├── tools/boundaries/ layering checker + __fixtures__ ├── packages/ │ ├── core-domain/ PURE TS — entities, invariants, costing, posting │ ├── core-application/ use cases, repository interfaces, permissions, audit │ ├── core-contracts/ zod schemas, DTOs, error codes │ ├── adapter-postgres/ Drizzle implementations │ └── shared-utils/ Money, Qty, UnitCost, Ulid, Clock └── apps/ ├── api/ NestJS — /health only at first └── web/ Vue 3 + Vite (added when phase 1 needs a screen)
Do NOT create these yet packages/adapter-sqlite-wasm (phase 12 — browser SQLite WASM + OPFS) and apps/mcp (phase 14). Empty folders are speculative scaffolding. The layering that makes them possible is what matters.

There is no apps/desktop — Tauri is rejected (D-20). Offline runs inside the PWA, so core-domain and core-application must also avoid Node built-ins (fs, path, crypto): they get bundled for the browser.

Manual bootstrap (if you set it up yourself)

cd ~/projects/shererp

pnpm init
mkdir -p packages/{core-domain,core-application,core-contracts,adapter-postgres,shared-utils}/src
mkdir -p apps tools/boundaries/__fixtures__ .github/workflows

cat > pnpm-workspace.yaml <<'EOF'
packages:
  - "packages/*"
  - "apps/*"
EOF

Each package gets a minimal package.json. Example for shared-utils:

cat > packages/shared-utils/package.json <<'EOF'
{
  "name": "@shererp/shared-utils",
  "version": "0.0.0",
  "private": true,
  "main": "./src/index.ts",
  "types": "./src/index.ts",
  "scripts": {
    "typecheck": "tsc --noEmit",
    "test": "vitest run"
  }
}
EOF

Repeat for @shererp/core-domain, @shererp/core-application, @shererp/core-contracts, @shererp/adapter-postgres. Then wire the one-way dependencies:

# domain may depend ONLY on shared-utils + zod
pnpm --filter @shererp/core-domain add @shererp/shared-utils@workspace:* zod

# application depends on domain
pnpm --filter @shererp/core-application add @shererp/core-domain@workspace:*

# adapter depends on application
pnpm --filter @shererp/adapter-postgres add @shererp/core-application@workspace:* drizzle-orm pg

# root dev tooling
pnpm add -Dw typescript vitest eslint dependency-cruiser tsx @types/node
Dependency direction is one-way and CI-enforced api → application → domain → shared-utils. core-domain imports only shared-utils and zod — never NestJS, Drizzle, pg, express or DOM types. pnpm test:boundaries must fail the build if this is violated, and there must be a deliberate bad fixture proving the checker actually catches it.

// apps/api/src/health/health.controller.ts
import { Controller, Get } from '@nestjs/common';

@Controller('health')
export class HealthController {
  @Get()
  check() {
    return { status: 'ok' };
  }
}
Controllers stay ≤ 20 lines A controller maps a DTO to a command, calls one use case, and maps the result back. No business rules, no SQL, no calculations. If a controller is growing, the logic belongs in core-application.

apps/web/vite.config.ts — proxy the API

import { defineConfig } from 'vite';
import vue from '@vitejs/plugin-vue';

export default defineConfig({
  plugins: [vue()],
  server: {
    host: true,          // needed so Windows can reach the WSL2 dev server
    port: 5173,
    proxy: {
      '/api': { target: 'http://localhost:3000', changeOrigin: true },
    },
  },
});
Runtime API URL, not build-time The Vue app must read its API base URL at runtime from /config.json, not from import.meta.env.VITE_API_URL. A baked-in URL forces a separate frontend build per on-premise customer and breaks the one-artifact rule (§6.5).

pnpm --filter @shererp/adapter-postgres add drizzle-orm pg

Migration commands

pnpm db:generate               # drizzle-kit generate — SQL from schema changes
pnpm db:migrate                # apply migrations to sher_dev
pnpm db:studio                 # drizzle-kit studio — browse data in a UI

# apply to the test database too
DATABASE_URL=$TEST_DATABASE_URL pnpm db:migrate
Every table carries these, from migration one tenant_id (ULID, from TenantContext — never from a request body or URL), ULID primary key generated in application code (no autoincrement), soft-delete columns, a version column, and created_at/updated_at. Money is an integer in minor units (scale 2), quantity scale 3, unit cost scale 4. Retrofitting any of these later is enormously expensive.

11Verify it works — the four gates

pnpm lint                      # zero warnings
pnpm typecheck                 # zero errors, no new `any`
pnpm test:boundaries           # layering intact — NEVER bypass this one
pnpm test                      # zero skipped tests

# all four in one go
check

Prove the boundary checker actually works

A checker that always passes is worse than no checker. Test it deliberately:

# temporarily add a forbidden import to a domain file
echo "import { Injectable } from '@nestjs/common';" >> packages/core-domain/src/index.ts

pnpm test:boundaries           # MUST FAIL — if it passes, the checker is broken

git checkout packages/core-domain/src/index.ts   # undo
Never weaken a gate to make it green Do not skip a test, loosen a lint rule, add an eslint-disable, cast to any, or add an exception to the boundary checker so a slice can be called done. If a gate fails, the slice is not complete — say so and fix the cause.

12Vertical slice development — the loop

One business feature at a time, complete, top to bottom. Never all backend, then all database, then all frontend, then tests.

Acceptance criteria + expected numbers ← WRITTEN BEFORE ANY CODE → Domain logic core-domain → Application use case core-application → Migration schema for THIS feature only → Repository/adapter adapter-postgres → API + contract core-contracts, apps/api → Vue screen apps/web → Unit tests domain, pure → Integration/DB tests → Permission + tenant-isolation tests → pnpm lint · typecheck · test:boundaries · test → Manual UI acceptance YOU, against the pre-written numbers → Commit → Next slice

How big is one slice?

This is one sliceThis is not
Create a product and see it in the product listThe entire product module
Search and filter products by brandAll of the backend for products
Record a purchase that creates a lot and increases stockAll migrations for phase 3
Pay a supplier and see the payable fallThe repository layer

If a slice cannot be demonstrated in the UI in under a minute, it is probably two slices.

Your working rhythm — one slice per agent conversation

  1. Pick the next slice from SRS_AND_BUILD_GUIDE.md §6.1.
  2. Write the expected numbers first — before any code exists. This is the single defence against silently accepting wrong AI output.
  3. Paste the prompt kernel + slice task block to the agent.
  4. Agent replies with a PLAN. This is the cheapest checkpoint — if it looks wrong, stop here.
  5. Approve → agent implements the full vertical: domain → use case → migration → repository → API → UI → tests.
  6. Agent pastes the real output of all four commands.
  7. Review the diff.
  8. Run the slice in the real UI yourself and check the numbers against step 2.
  9. Commit.
A slice is not done because the backend compiles It is not done because tests pass, or because the API returns 200. It is done when the feature works in the real UI and you have personally confirmed the numbers match what you wrote down beforehand.

The ten-step write path — check every mutation has all ten, in one transaction

1 resolve TenantContext 2 permission check (entitlement → feature → setting → permission → access) 3 idempotency check (operation_id) 4 PeriodGuard.assertOpen(business_date) 5 load aggregates 6 domain invariants 7 persist changes 8 post journal + stock movements 9 write audit event 10 commit ONE database transaction. All ten steps, or reject.

13Slice review checklist

Run through this on every diff before you commit. Use a different model than the one that wrote the code to review it — the agent that wrote the bug cannot catch it, because its own tests agree with its own mistake.

Undoing things

git restore <file>             # discard unstaged changes to a file
git restore --staged <file>    # unstage, keep changes
git reset --soft HEAD~1        # undo last commit, keep changes staged
git reset --hard HEAD          # DANGER: discard everything uncommitted
git stash / git stash pop      # park work temporarily
git clean -nd                  # preview untracked files that would be deleted
Commit before letting an agent loose A clean working tree means git diff shows you exactly what the agent changed, and git reset --hard is a one-command undo if it goes wrong.
